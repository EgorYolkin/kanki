# Вклад в Kanki

## Перед изменением

1. Прочитайте `AGENTS.md`, `tasks/plan.md` и статус этапов в `tasks/todo.md`.
2. Создайте GitHub issue для конкретной задачи и заполните его до начала работы: цель, границы (что не входит), зависимости, упорядоченный план в чекбоксах, проверяемые критерии приёмки и способ проверки. Этапный issue может быть родительским, но отдельный task issue обязателен; без него реализацию не начинают. Для уязвимостей и приватных данных сначала используйте приватный канал GitHub, а не публичный issue.
3. Обновите `dev` и создайте отдельную ветку от него: `feature/<тема>`, `fix/<тема>` или `docs/<тема>`. Никогда не реализуйте изменения и не коммитьте в `main` или `dev` напрямую. В сообщениях коммитов ссылайтесь на issue (`refs #N`). Не фиксируйте восьмиполевый нотетайп и контракты синхронизации до Э1; не представляйте заглушку как работающую функцию.

## Ведение задачи

- По ходу работы отмечайте в issue выполненные пункты плана и добавляйте комментарии с фактическими результатами проверки. Не отмечайте непроверенное и не скрывайте блокеры.
- Если задача распалась или появился блокер, обновите issue: сузьте объём, добавьте зависимость или создайте связанный follow-up issue. Незавершённая задача остаётся открытой.
- После реализации и проверки запушьте ветку и откройте PR в `dev` с `Closes #N`. В описании PR укажите изменения, коммиты, фактическую проверку, риски и отложенное. PR не заменяет ведение issue.
- После ревью и merge убедитесь, что task issue закрылся; при необходимости закройте его со ссылкой на PR. Для принятого этапа обновите `tasks/todo.md` и этапный issue.

## Реализация

- Swift 6, SwiftUI, минимум iOS 17. Пользовательский текст — по-русски; имена типов и коммиты — по-английски.
- Поведение живёт в `Kanki/Domain/` и покрывается unit-тестами; `Kanki/Views/` — только вёрстка и локальные флаги показа. Любой новый доменный тип приходит вместе с `<Type>Tests`.
- `project.yml` — источник конфигурации; после изменения состава файлов `Kanki/` выполните `xcodegen generate` и закоммитьте `Kanki.xcodeproj`. Не редактируйте `.xcodeproj` вручную.
- Не добавляйте секреты, реальные заметки или экспорт коллекции Anki в репозиторий. Для демонстраций используйте синтетические данные с явной маркировкой.
- Сохраняйте совместимость с текущим этапом: новые зависимости и слои архитектуры появляются только вместе с потребляющим их поведением.

## Проверка

Полный контур — те же команды, что выполняет CI (`.github/workflows/ci.yml`):

```bash
./scripts/lint.sh      # SwiftLint --strict и markdownlint-cli2
./scripts/test.sh      # KankiTests + порог покрытия 95 % по Kanki/Domain
./scripts/ui-test.sh   # четыре UI-теста на симуляторе
./scripts/ci.sh        # всё перечисленное по порядку
```

Порог покрытия и состав проверок описаны в `docs/quality-gates.md`. Снижать порог, отключать правило линтера или шаги CI можно только отдельным issue; `continue-on-error` и `|| true` в проверках запрещены. При наличии simulator runtime запустите приложение и проверьте затронутые переходы/экраны. Если runtime или платформа отсутствуют, укажите точную причину и не называйте сборку, запуск или тесты успешными. Проверяйте изменённый пользовательский сценарий, а не только компиляцию.

## Gitflow

- Рабочая ветка → PR в `dev`; после проверки и ревью — merge в `dev`.
- Выпуск: отдельный PR `dev` → `main`. В `main` изменения попадают только этим путём; прямые push и force-push в `main`/`dev` запрещены.
- Перед коммитом убедитесь, что находитесь в рабочей ветке. При открытии PR проверьте базовую ветку; для фич, исправлений и документации это `dev`.

## Pull request

Заполните `.github/pull_request_template.md`: связанный issue и `Closes #N`, поведение, границы, фактические команды и результаты, риски и скриншот для UI (если удалось запустить). Не отмечайте непроверенные пункты выполненными. Не отправляйте незавершённую реализацию под видом готовой. PR открывается после реализации и проверки; если проверка выявила незавершённость, оставьте issue открытым и укажите оставшуюся работу.

Сообщения о нарушениях поведения см. `CODE_OF_CONDUCT.md`. Для передачи конкретной задачи агенту используйте `docs/agent-task-template.md`.
