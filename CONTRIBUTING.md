# Вклад в Kanki

## Перед изменением

1. Прочитайте `AGENTS.md`, `tasks/plan.md` и статус этапов в `tasks/todo.md`.
2. Опишите одну проверяемую задачу: какое поведение меняется, что не входит в задачу, как его проверить.
3. Обновите `dev` и создайте отдельную ветку от него: `feature/<тема>`, `fix/<тема>` или `docs/<тема>`. Никогда не реализуйте изменения и не коммитьте в `main` или `dev` напрямую. Не фиксируйте восьмиполевый нотетайп и контракты синхронизации до Э1; не представляйте заглушку как работающую функцию.

## Реализация

- Swift 6, SwiftUI, минимум iOS 17. Пользовательский текст — по-русски; имена типов и коммиты — по-английски.
- `project.yml` — источник конфигурации; после изменения состава файлов `Kanki/` выполните `xcodegen generate`. Не редактируйте `.xcodeproj` вручную.
- Не добавляйте секреты, реальные заметки или экспорт коллекции Anki в репозиторий. Для демонстраций используйте синтетические данные с явной маркировкой.
- Сохраняйте совместимость с текущим этапом: новые зависимости и слои архитектуры появляются только вместе с потребляющим их поведением.

## Проверка

Для текущего скелета:

```bash
xcrun --sdk iphonesimulator swiftc -typecheck -parse-as-library \
  -target arm64-apple-ios17.0-simulator Kanki/KankiApp.swift
xcodebuild -project Kanki.xcodeproj -scheme Kanki -configuration Debug \
  -destination 'generic/platform=iOS Simulator' build
```

При наличии simulator runtime запустите приложение и проверьте затронутые переходы/экраны. Если runtime или платформа отсутствуют, укажите точную причину и не называйте сборку или запуск успешными. Для будущих изменений проверяйте изменённый пользовательский сценарий, а не только компиляцию.

## Gitflow

- Рабочая ветка → PR в `dev`; после проверки и ревью — merge в `dev`.
- Выпуск: отдельный PR `dev` → `main`. В `main` изменения попадают только этим путём; прямые push и force-push в `main`/`dev` запрещены.
- Перед коммитом убедитесь, что находитесь в рабочей ветке. При открытии PR проверьте базовую ветку; для фич, исправлений и документации это `dev`.

## Pull request

Заполните `.github/pull_request_template.md`: поведение, границы, фактические команды и результаты, риски и скриншот для UI (если удалось запустить). Не отмечайте непроверенные пункты выполненными. Не отправляйте незавершённую реализацию под видом готовой.

Сообщения о нарушениях поведения см. `CODE_OF_CONDUCT.md`. Для передачи конкретной задачи агенту используйте `docs/agent-task-template.md`.
