# Вклад в Kanki

## Перед изменением

1. Прочитайте `AGENTS.md`, [GIT_WORKFLOW.md](GIT_WORKFLOW.md), `tasks/plan.md` и статус этапов в `tasks/todo.md`. Git-операции выполняйте только после чтения workflow.
2. До изменений выполните раздел «Задача и изоляция веток» в workflow: отдельный task issue с планом и критериями, рабочая ветка от актуального `origin/dev`. Этапный issue не заменяет task issue; приватные данные и уязвимости не отправляются в публичный issue.
3. Не фиксируйте восьмиполевый нотетайп и контракты синхронизации до Э1; не представляйте заглушку как работающую функцию.

## Ведение задачи

Порядок коммитов, ведения issue, публикации и закрытия задачи определён в
[GIT_WORKFLOW.md](GIT_WORKFLOW.md). Записывайте фактические результаты проверки
и блокеры; незавершённая задача остаётся открытой.

## Реализация

- Swift 6, SwiftUI, минимум iOS 17. Пользовательский текст — по-русски; имена типов и коммиты — по-английски.
- Поведение живёт в `Kanki/Domain/` и покрывается unit-тестами; `Kanki/Views/` — только вёрстка и локальные флаги показа. Любой новый доменный тип приходит вместе с `<Type>Tests`.
- `project.yml` — источник конфигурации; после изменения состава файлов `Kanki/` выполните `xcodegen generate` и закоммитьте `Kanki.xcodeproj`. Не редактируйте `.xcodeproj` вручную.
- Не добавляйте секреты, реальные заметки или экспорт коллекции Anki в репозиторий. Для демонстраций используйте синтетические данные с явной маркировкой.
- Сохраняйте совместимость с текущим этапом: новые зависимости и слои архитектуры появляются только вместе с потребляющим их поведением.

## Проверка

Полный локальный контур включает iOS UI-тесты, которых нет в per-PR CI:

```bash
./scripts/lint.sh      # SwiftLint --strict и markdownlint-cli2
./scripts/test.sh      # KankiTests + порог покрытия 95 % по Kanki/Domain
./scripts/ui-test.sh "$simulator_id" # iOS UI-тесты на отдельном iPhone 17e
./scripts/ci.sh "$simulator_id"      # всё перечисленное по порядку
```

Выбор `simulator_id` описан в [контуре качества](docs/quality-gates.md#команды).

Порог покрытия и состав проверок описаны в `docs/quality-gates.md`. Снижать порог, отключать правило линтера или шаги CI можно только отдельным issue; `continue-on-error` и `|| true` в проверках запрещены. При наличии simulator runtime запустите приложение и проверьте затронутые переходы/экраны. Если runtime или платформа отсутствуют, укажите точную причину и не называйте сборку, запуск или тесты успешными. Проверяйте изменённый пользовательский сценарий, а не только компиляцию.

## Gitflow

Ветки, разрешения на Git-операции, направления PR, ревью и выпуск описаны только
в [GIT_WORKFLOW.md](GIT_WORKFLOW.md). Прочитайте его до работы с Git.

## Pull request

Заполните [.github/pull_request_template.md](.github/pull_request_template.md)
по разделу «Публикация, интеграция и выпуск» в workflow. Не отмечайте непроверенные
пункты выполненными и не отправляйте незавершённую реализацию под видом готовой.

Сообщения о нарушениях поведения см. `CODE_OF_CONDUCT.md`. Для передачи конкретной задачи агенту используйте `docs/agent-task-template.md`.
