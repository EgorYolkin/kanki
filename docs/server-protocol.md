# Серверный протокол Kanki

Решение для первого серверного среза: приложение и агенты ходят в один
REST/JSON API по `https://kanki.host`; SSH используется только для установки и ops.
Это единственный публичный адрес: прежний `kanki.ink` выведен из конфигурации
сервера 2026-11-03, его домен не делегирован в DNS (см. «Домен и сертификат»).

## Выбор

| Слой | Решение | Причина |
| --- | --- | --- |
| Транспорт | HTTPS `kanki.host` (nginx + Let's Encrypt) на 144.31.57.107 | публичный домен, TLS на уровне приложения; uvicorn только на `127.0.0.1` |
| API | REST + JSON, `/v1`, OpenAPI 3.1 | `URLSession`, curl, отладка, агенты |
| Аутентификация | `Authorization: Bearer` | отдельные токены устройства/агентов, отзыв |
| Хранение | SQLite WAL, `busy_timeout`, `synchronous=NORMAL` | один писатель, конкурентные чтения |
| Обмен | снимок + `revision`/`base_revision`, `409` | без ложного мержа и потери чужих правок |
| Агенты | OpenAPI + MCP stdio | один API, два способа доступа |
| SSH | rsync + systemd user service | деплой и диагностика, не канал данных iOS |

Почему не gRPC: Swift-клиент и агенты получают лишний тулчейн, а выигрыш для
одного пользователя и редких снимков не оправдан. Почему не SSH из приложения:
iOS-приложению пришлось бы хранить SSH-ключи и реализовывать SSH-клиент; для
данных это не нужно.

## Контракт `/v1`

- `GET /v1/health` — без токена: `{status, version, time}`.
- `GET /v1/me` — `{label, role}` для проверки токена.
- `GET /v1/snapshot` — `{revision, schema_version, data, updated_at}`;
  при отсутствии данных `revision = 0`, `data = null`. Ответ содержит
  `ETag: "<revision>"`; запрос с `If-None-Match` этой ревизии (или `*`,
  включая слабый `W/`-вариант) отвечает `304` без тела.
- `PUT /v1/snapshot` — `{schema_version, base_revision, data}`.
  Успех возвращает новую ревизию; несовпадение `base_revision` — `409` с
  `detail.current_revision`. Запись атомарная, лимит 10 МиБ.
- `POST /v1/publish` — атомарно публикует пакет Markdown-документов.
- `GET /v1/export.apkg` — возвращает текущие опубликованные заметки в `.apkg`.
- `GET /v1/changes?since=0` и `POST /v1/changes` — отдельный поток публикаций и журнала импортированных карт.
- `POST /v1/tokens` `{label}` → `{id, label, token}`; plaintext один раз.
- `GET /v1/tokens`, `DELETE /v1/tokens/{id}` — только admin.

Токены: bootstrap admin из `KANKI_ADMIN_TOKEN`; остальные — случайные 32 байта,
в БД только SHA-256. Сравнение admin-токена — `hmac.compare_digest`.

## Публикация Markdown и экспорт Anki

Оба маршрута требуют действующий admin- или device-токен. Как и у снимка,
хранилище одно на сервер, а не отдельное для каждого токена.

`POST /v1/publish` принимает `application/json`: объект с единственным ключом
`documents`, массивом из 1–100 строк. Всё тело — до 1 МиБ. Одна строка, то есть
один Markdown-документ, задаёт одну заметку. В начале нужен YAML frontmatter с
разделителями `---` на отдельных строках:

```markdown
---
uid: n-018f3a2b-7c41-7000-8000-000000000001
schema_version: 1
kind: fact
title: Синтетический пример
question: Что обозначает A?
answer: "**A** — условная метка."
sources:
  - ref: synthetic-example
    locator: Раздел 1
relations:
  - t: requires
    to: n-018f3a2b-7c41-7000-8000-000000000002
---
Текст заметки в **Markdown**.
```

- `uid` и `relations[].to` — `n-` и канонический UUIDv7 в нижнем регистре.
  Целевую заметку можно опубликовать позже.
- `schema_version` — целое `1`; `kind` — `concept`, `fact` или `source`.
  `title` и `body` непустые. `body` задаётся либо после frontmatter, либо
  строковым полем `body` во frontmatter, но не одновременно.
- `question` и `answer` обязательны, но могут быть пустыми строками (`""`).
  `sources` и `relations` обязательны, но могут быть пустыми массивами (`[]`).
  Для источника нужен непустой `ref`; `locator` — необязательная строка.
  Для связи нужны `t` (`requires`, `part_of`, `related`, `contrast`) и `to`;
  `note` — необязательная строка. Экспорт сохраняет порядок канонических связей.
- Лишние и повторяющиеся ключи, YAML-алиасы, недопустимые управляющие символы
  и повтор одного UID в запросе отклоняются. Индексы документов в ошибках — с нуля.

Успех (`200`) возвращает `{"notes":[{"uid":"n-…","guid":"…","mod":1800000000}]}`
в порядке запроса. Новая заметка получает `genanki.guid_for(uid)`. Повтор
равных разобранных данных возвращает тот же результат и не меняет запись.
Правка того же UID заменяет её целиком, сохраняет GUID и увеличивает `mod`
даже при двух правках за секунду. Пропуск UID ничего не удаляет.
Невалидный пакет не пишет ни одной заметки: `422 invalid_publication` для
JSON-конверта, `422 invalid_document` или `duplicate_uid` с `document_index`
для документа. Другие отказы: `401` для токена, `413 publication_too_large`,
`415 expected_json`, `409 guid_conflict` при коллизии идентичности.

`GET /v1/export.apkg` читает все опубликованные заметки из SQLite, отдельно
от `/v1/snapshot`. Возвращает `200 application/zip` с вложением `kanki.apkg`
или `404 no_publications`, если экспортировать нечего. Пакет следует
[контракту Anki v1](anki-exchange-v1.md): восемь полей, одна новая карта
`ord=0` на заметку, без медиа, истории или расписания повторений.
При пустом вопросе карточка показывает экранированный заголовок.
Карточки используют только сгенерированную разметку: абзацы, выделение,
списки, код и абсолютные ссылки `http(s)`. Входные HTML и JS не исполняются;
встроенные изображения, формулы и произвольные шаблоны не поддерживаются.
Текст и связи обновляются при импорте в Anki по сохранённому GUID; сервер
не получает историю обучения из Anki и не мержит её.

## Снимок и ревизии

`data` — JSON-объект текущего `LearningSnapshot` (ручные карточки, оценки и
их FSRS-расписание). Сервер не интерпретирует поля и не мержит их. Клиент обязан
перечитать `revision` перед записью; при `409` показывается конфликт, а не
повторная запись вслепую. Delta-обмен не меняет этот контракт.

`schema_version: 1` — предварительная версия серверного снимка, не поле
`SchemaVersion` из [контракта Anki v1](anki-exchange-v1.md). Снимок не включает
импортированные заметки, связи и исходный прогресс Anki.

Клиент отклоняет снимок с повторяющимися ID карточек при декодировании и перед
заменой локального файла; прежние байты сохраняются при отказе записи.
Ключи расписаний нормализуются как UUID: разные строковые ключи одного UUID
(например, в разном регистре) считаются ошибкой данных, а не объединяются.

Клиент сравнивает локальный снимок с серверным на точности провода
(ISO-8601 с точностью до секунды): доли секунды теряются при сериализации,
поэтому локальный снимок перед сравнением проходит такой же round-trip. Это
позволяет отличить «PUT применён, но ответ потерян» (достаточно принять
ревизию) от настоящего конфликта. Снимок с `snapshot_version` или
`schema_version` новее поддерживаемой клиент отклоняет ошибкой, а не
декодирует с дефолтами — иначе незнакомые поля были бы стёрты следующей
правкой.

Авто-push и ручной обмен из настроек используют общий `PushGate` в `AppShell`.
Каждая сохранённая правка меняет поколение: подтверждение PUT очищает dirty-флаг
только для отправленного поколения. Правка во время PUT требует следующей отправки,
не дожидаясь дебаунса. GET применяется только при неизменных поколении и ревизии
без пересекающейся записи или ручного обмена. Ручная операция при летящем PUT
просит дождаться его завершения, не отменяя уже отправленный запрос.

После замены снимка оба активных сеанса повторения закрываются. Оценка проверяет,
что карточка остаётся активной и её содержимое совпадает с показанным; расчёт
расписания и сохранение кандидата завершаются до изменения состояния экрана.

## Delta импортированных карточек

Оба маршрута требуют bearer-токен и используют общую серверную БД, как публикации и снимок.
Существующие публикации попадают в поток при первой миграции; новые правки попадают туда
в одной транзакции с записью публикации. Равная повторная публикация не создаёт событие.

- `GET /v1/changes?since=0` возвращает `{stream, changes, more}`. `stream` — UUID
  потока; `changes` — до 50 записей `{seq, anchor, event}` по возрастанию.
  Следующий запрос передаёт `since=<последний seq>&anchor=<его UUID>`. Пустая
  страница не меняет курсор. На `since=0` параметр `anchor` не передаётся.
- `POST /v1/changes` принимает `{stream, since, anchor?, events}` (до 50 событий
  и 1 МиБ полного JSON-тела) и отвечает `{accepted: [id, …]}` в порядке запроса.
  Сервер проверяет курсор в той же транзакции, в которой пишет события. Точный
  повтор сохраняет прежний `seq` и `anchor`; повтор ID с другим содержимым
  отклоняет весь пакет (`409 event_id_conflict`). Для другой базы — `409 stream_mismatch`.
- `409 future_cursor` означает курсор за концом потока, а `409 anchor_mismatch` —
  отсутствующий или несовпадающий UUID при имеющемся `seq`. UUID создаётся заново
  для каждой новой записи, даже если восстановленная БД повторно использовала
  тот же `seq` для тех же данных. Delta и публикации пишутся в WAL с
  `synchronous=FULL`; режим снимка не изменился.

| `event.kind` | Поля | Направление |
| --- | --- | --- |
| `publication` | `note: {guid, modelID, mod, fields}` — поля того же нотетайпа, что в `.apkg`. | Сервер → клиент |
| `review` | `id` (UUID, нижний регистр), `uid` (UID заметки v1), `guid`, `ord`, `reviewedAt` (Unix-секунды с дробной частью), `rating` (`1…4`). | Клиент ↔ сервер |
| `progress` | `id`, `uid`, `guid`, `ord`, `progress: {due, ivl, queue, reviews}`. До 100 строк revlog на событие; поля v1 и исходные единицы сохранены. | Клиент ↔ сервер |

В «Настройки → Импортированные карточки → Обменяться изменениями» клиент
проверяет UUID потока и применяет страницу вместе с курсором до отправки журнала.
Сбой POST (`503`, `409` или неполный ACK) не отменяет уже полученную страницу;
состояния чтения и отправки показаны отдельно. Оценка, исходящий ID и локальный
FSRS сохраняются атомарно, а очередь очищается только после точного подтверждения ID.
Клиент ограничивает пакет по фактическим байтам JSON. При `413` делит пакет, а
событие, которое не помещается отдельно, сохраняет в карантине, не задерживая остальные.

Оценка и прогресс относятся только к совпадающему `(uid, guid, ord)`. До появления
карты наблюдения остаются в журнале, но запись с другой парой UID/GUID не влияет
на карту, её историю или приостановку. Клиент показывает число записей в карантине.
При восстановлении несовпадение UUID потока или якоря останавливает обмен;
автоматической перепривязки или восстановления истории нет.
При обновлении с чернового протокола сервер создаёт новый UUID потока и оставляет
старые наблюдения без UID отдельно. Клиент сохраняет их, но не принимает за
проверенные и не подменяет старый привязанный курсор новым.

При расхождении опубликованной и локально импортированной заметки без общей
версии клиент сохраняет обе и показывает счётчик расхождений. Для Anki сохраняется
первый принятый комплект `due/ivl/queue`: при создании карты и публикацией, и
импортом `.apkg` сначала применяются ранее полученные совпадающие наблюдения в
порядке записи журнала, затем данные пакета. Альтернативная запись остаётся
в журнале; разные ID revlog добавляются, а коллизия ID не перезаписывает
исходную строку. `queue = -1` помечает карту как приостановленную. Сырые `due` и `ivl`
не трактуются как сроки FSRS. Оценки Kanki, пришедшие из потока, попадают в историю,
но не переписывают FSRS другого устройства.

## Безопасность и HTTPS

- uvicorn слушает только `127.0.0.1:8000`; наружу API отдаёт nginx
  (`/etc/nginx/sites-enabled/kanki`) с сертификатом Let's Encrypt, HTTP
  перенаправляет на HTTPS (301), порт 8000 в интернет не опубликован.
- nginx закрывает `/docs`, `/redoc`, `/openapi.json` и `/v1/tokens` извне
  (404), ограничивает частоту запросов (`limit_req`), шлёт HSTS,
  `X-Content-Type-Options` и `Referrer-Policy`.
- iOS ATS: HTTPS-домен проходит штатную политику; ранее добавленный
  `NSAllowsArbitraryLoads` (#77) можно убрать, когда plaintext-адреса
  больше не используются.
- Токен на подписанной сборке — Keychain; в неподписанном симуляторе без
  entitlement используется файл в sandbox с file protection и правами `0600`.
- Delta требует HTTPS и не следует редиректам. Необязательный пин — канонический
  Base64 от SHA-256 DER SPKI P-256 ключа сертификата сервера. Пин не заменяет
  проверку цепочки и имени хоста; на новый ключ пин нужно обновить вручную.
  Отдельный локальный прогон описан в [Э4](../experiments/README.md#э4-tls-и-pinning).
- У delta и снимка отдельные адреса и секреты, привязанные к origin
  (схема, хост и порт). Delta сохраняет настройки только после HTTPS, проверки
  пина при его наличии и проверки потока. Изменение черновика адреса снимка
  не переключает автоматический обмен. Старый токен без origin нужно ввести заново.
- `.env`, токены и база не коммитятся.

## Домен и сертификат

- `kanki.host` — единственный адрес API: `A`-запись на `144.31.57.107`,
  сертификат Let's Encrypt в `/etc/letsencrypt/live/kanki.host/`
  (`notAfter` 2027-02-01), продление через `snap.certbot.renew.timer`.
- Vhost `/etc/nginx/sites-enabled/kanki` состоит из двух блоков: `:80`
  (ACME-челлендж и redirect на HTTPS) и `:443` (TLS и прокси). Общие части
  вынесены в `/etc/nginx/snippets/kanki-tls.conf` (TLS 1.2/1.3, HSTS,
  заголовки, лимит тела 11m) и `kanki-proxy.conf` (маршруты `/v1/` и
  `/webhooks/`, 404 на `docs`, `redoc`, `openapi.json`, `/v1/tokens`).
- `kanki.ink` выведен из конфигурации: серверных блоков для него нет. Его
  сертификат (`/etc/letsencrypt/live/kanki.ink/`) остаётся на диске до
  истечения 2027-01-31 и продлеваться не будет.
- `certbot renew --dry-run` на этом хосте не проходит: исходящие соединения к
  `acme-staging-v02.api.letsencrypt.org` сбрасываются. Production ACME доступен,
  выдача и продление идут через него; проверять продление лучше по
  `snap.certbot.renew.service` и сроку сертификата.

## Доступ агентов

- REST: `curl`/OpenAPI `/docs` с токеном агента.
- MCP: `uv run --project server kanki-mcp` по stdio; инструменты `health`,
  `me`, `get_snapshot`, `put_snapshot`. Агент обязан передавать `base_revision`
  из последнего `get_snapshot`.
- SSH: деплой, `journalctl --user -u kanki-server`, выдача/отзыв токенов.

## Границы

- Delta запускается вручную; нет фонового обмена, удаления по отсутствию, автоматической
  смены потока и разрешения сохранённых расхождений.
- Нет многопользовательского доступа и прав на отдельные карточки.
- Нет AnkiMobile custom sync или переноса внутреннего состояния FSRS из Anki.

Инструкции по запуску, деплою и MCP — в [server/README.md](../server/README.md).
