# Спецификация MVP: iOS-приложение «заметки + граф + SRS» с совместимостью Anki

Дата: 2026-11-01 (ред. 2, после внутренней критики). Статус: проектная спецификация с открытыми блокерами — см. §13.1 «Блокеры решения». Все проверки документации выполнены 2026-11-01 в исследовательской сессии (docs.ankiweb.net: exporting.html, importing/text-files.html, importing/packaged-decks, media, editing, templates/intro, sync-server; исходники ankitects/anki HEAD 136bd42 от 2026-10-29; github.com/groue/GRDB.swift/releases; github.com/open-spaced-repetition/swift-fsrs; letsencrypt.org). Обозначения: **[Ф]** — факт, подтверждённый первичным источником с цитатой; **[Ф2]** — факт со слов вторичного источника, первичная проверка не выполнялась; **[Р]** — рекомендация (решение); **[Г]** — гипотеза/эвристика, не проверенная эмпирически.

---

## 1. Рекомендуемое решение простым языком

Мы строим свою базу знаний как в Obsidian (заметки, типизированные связи, граф, обратные ссылки) с интервальным повторением (FSRS), а совместимость с Anki обеспечиваем через .apkg как «обменной валютой».

Ядро решения:

1. **Источник истины — наш сервер** с SQLite-базой. ИИ-агент публикует контент на сервер через обменный формат (строго схематизированный Markdown+frontmatter с UID). Канон связей — поле Relations заметки в обменном формате/БД; таблица `edges` — полностью перестраиваемый индекс, не источник.
2. **Каждая заметка имеет UID** (например `n-<uuidv7>`). UID кладётся в **первое поле** Anki-заметки, Title — во второе. Опора: текстовый импорт матчит по первому полю («Anki uses the first field to determine if a note is unique» — docs.ankiweb.net/importing/text-files.html, 2026-11-01), а .apkg-импорт матчит по **guid** (rslib/src/import_export/package/apkg/import/notes.rs:338-347, HEAD 136bd42) — guid генерируется детерминированно из UID один раз и никогда не меняется. [Ф+Р]
3. **Свой тип заметки** ObsidianTyped с полями UID/Title/Body/Question/Answer/Relations/Sources/SchemaVersion. Перенос кастомного нотетайпа в .apkg подтверждён (notes.rs:139-153, packaged-decks); сама композиция полей — гипотеза, **фиксируется только после эксперимента Э1** (§12). [Г]
4. **Уровень 2 (повтор в стандартных клиентах) реализуется двумя каналами**, с разной степенью доказанности: (а) контент доезжает .apkg-импортом — подтверждено документацией [Ф]; (б) прогресс репетируется на нашем сервере через официальный встроенный `anki --syncserver` — серверная часть подтверждена документацией [Ф: sync-server.md], а **наличие custom sync URL в AnkiMobile первичным источником не подтверждено** — см. §3 и §13.1; если не подтвердится, для AnkiMobile уровень 2 сводится к .apkg-каналу (прогресс живёт в десктопе/AnkiDroid). [Р]
5. **Граф, типизированные связи, обратные ссылки, зависимое планирование — только в нашем приложении** (уровень 3). В стандартных клиентах Relations — читаемый текст, карточки самодостаточны.
6. **Потоки однонаправлены:** контент — только от агента (и от ручного редактора в приложении — §9, сценарий 9) через сервер; правки в Anki игнорируются («в Anki только репетировать»); scheduling мержится по правилу соответствия карточек (§8.2); конфликты контента и связей не мержатся автоматически — очередь `conflicts/`.

Пользователь один, сервер есть, домена нет — закрывается self-signed-сертификатом с SPKI-pinning (базовый план) либо Tailscale (альтернатива, зависит от ответа на вопрос §13.3).

## 2. Подтверждённые возможности и ограничения Anki

Проверено 2026-11-01 в docs.ankiweb.net и/или исходниках ankitects/anki (HEAD 136bd42), если не указано иное.

**Возможности:**

- .apkg содержит cards, notes, note types, decks и медиа одной колоды (с «Include Scheduling Information» — и историю повторов). exporting.html. [Ф]
- .colpkg — вся коллекция; импорт заменяет её, .apkg — добавляет/обновляет. exporting.html, packaged-decks. [Ф]
- Импорт .apkg матчит по **guid** (notes.rs:338-347); guid — base91 от случайного u64 (rslib/src/notes/mod.rs:146). [Ф]
- Обновление при .apkg-импорте — по mtime («If the notes in the file are newer than your local copy…» — packaged-decks). Следствие: монотонно увеличиваем mod при каждом экспорте. [Ф+Р]
- Текстовый импорт матчит по **первому полю**; повторный импорт обновляет заметки и сохраняет планирование («the existing scheduling information on all their cards will be preserved» — importing/text-files.html). [Ф]
- Прогресс управляется независимо: экспорт «Include Scheduling Information», импорт «Import any learning progress» (23.10+). [Ф]
- Кастомный тип заметки допустим и переносится в .apkg/.colpkg (notes.rs:139-153; packaged-decks). Запрещённые имена полей: `Tags`, `Type`, `Deck`, `Card`, `FrontSide` (editing.html). [Ф] Про верхний предел числа полей: в schema11.rs константа максимума не найдена grep'ом по MAX_FIELD*/max_fields — это **отсутствие находки, а не доказательство отсутствия лимита**; для 8-полевого нотетайпа лимит не критичен. [Г]
- Официальный self-hosted sync server (`anki --syncserver`, 2.1.57+), аутентификация `SYNC_USER1=user:pass`, пример `http://192.168.1.200:8080/` — sync-server.md. [Ф] Custom sync URL подтверждён для **AnkiDroid** (настройка в разделе Advanced — **источник: документация AnkiDroid, в этой сессии не открывалась, статус [Ф2]**) и для **AnkiDesktop**; для **AnkiMobile — только [Ф2] по вторичным источникам, первично не проверено** — это главный открытый пункт уровня 2 (см. §13.1).
- Теги в Anki — метаданные заметки **вне набора полей** (свойство note, не field); тег `archived:<run_id>` кладётся в note.tags без изменения нотетайпа. [Ф: схема notes.tags в collection.anki2; точную колонку проверить при имплементации — [Г] на уровне имени колонки]
- Медиа: HTML в полях, изображения/аудио по именам файлов из media-манифеста; mp3/mp4 наиболее совместимы (media). [Ф]

**Ограничения:**

- Markdown-экспорта нет; текстовый экспорт — TSV со встроенным HTML. [Ф]
- Нет типизированных связей, графа, внутренних ссылок заметка→заметка; ссылки из карточек открываются внешне (qt/aqt/webview.py:157,272,502; qt/aqt/utils.py:123); обходное — десктопные дополнения. Утверждение «AnkiMobile не поддерживает дополнения» — из общедоступных описаний платформы, в этой сессии первично не проверялось. [Ф2]
- Обновление «generally not possible if the note type is changed» (packaged-decks); guid-матч с другим нотетайпом → заметка игнорируется (notes.rs:753). [Ф]
- Один профиль не может синхронизироваться одновременно с AnkiWeb и кастомным сервером. [Ф]
- PDF переносится в media, но надёжного inline-показа на AnkiMobile/AnkiWeb нет. [Ф]
- Имена медиа: спецсимволы вырезаются, длинные обрезаются; ASCII без пробелов. [Ф]
- Переносимость JS в шаблонах не документирована — отсутствие документации подтверждено чтением templates/intro, fields, styling; эмпирически поведение JS не проверялось. Решение: **MVP не использует JS в шаблонах вовсе** и использует согласованное минимальное HTML-подмножество (§7.1). [Г→Р]

## 4. Сравнение вариантов источника истины и выбор

| Критерий | A: Markdown+frontmatter | B: модель Anki как источник | **C: своя нормализованная модель + обменный формат** |
|---|---|---|---|
| Удобство агента и ручного редактирования | Отличное | Плохое (HTML-поля) | Хорошее |
| Связи | Wikilinks теряются в Anki | Строка в поле без схемы | Типизированные, валидируемые |
| Совместимость с Anki | Потеря связей | Максимальная | Высокая (UID в первом поле — штатная дедупликация и сохранение scheduling [Ф]) |
| iOS-клиент | Парсинг текстовых соглашений | Чтение непубличной SQLite-схемы | Самый простой |
| Стоимость | Lossy HTML→markdown | Хрупкость, не публичный API | Два однонаправленных конвертера + SchemaVersion |

**Выбор: вариант C** — при условии успешного Э1 (без него решение преждевременно, §13.1).

## 5. Схема сущностей и связей

**Сущности:**

- **Note**: `uid` (PK, `n-<uuidv7>`), `kind` (concept|fact|source), `title`, `body` (markdown), `question`, `answer`, `sources`, `schema_version`, `deleted` (soft-delete), `created`, `modified`, `mod` (монотонный epoch для mtime-обновлений Anki), `guid` (детерминирован из uid, никогда не меняется), `base_hash` (sha256 от канонического представления title+body+relations+sources — **включая Relations и Sources**, §8.3).
- **Card**: `card_uid` (`c-<uuidv7>`), `note_uid`, `ord` (порядковый номер карточки внутри заметки, 0-based, стабилен), `deck`, `progress_policy`, **`suspended` (bool)**, **`archived_tag` (nullable)**. Соответствие Anki-карте: **(note.guid, ord)** — ord Anki-карты внутри ноты стабилен, пока не меняется число карточек нотетайпа; правило сопоставления для мержа прогресса — §8.2.
- **Relation**: `rel_uid` (`r-<uuidv7>`), `from_note`, `to_note`, `rel_type`.
- **Source (материал)** — в MVP поле заметки; отдельный узел kind=source отложен.
- **ReviewLog** — собственная таблица с колонками, отображаемыми на revlog Anki: `ts_ms, card_uid, anki_cid(nullable), ease, ivl_days, last_ivl_days, factor, time_s, revlog_type(0..4)`. **Маппинг типов записей Anki revlog (learn/review/relearn/cram) в семантику swift-fsrs не разобран и первичным источником в этой сессии не подтверждён** — точные имена/номера колонок и семантику сверить со схемой collection.anki2 при имплементации (добавлен шаг в Э6). [Г]
- **Provenance** — отдельная таблица `note_provenance(note_uid, run_id, prompt_version, model, published_at)`: у заметки поля provenance нет (поправка к ред. 1), `op: touch` обновляет именно эту таблицу (§8.1).

**Типы связей (4 на MVP):**

| Тип | Направление | Хранение | Инверсия |
|---|---|---|---|
| `requires` | A→B «A требует B» | только каноническое (от зависимого к требуемому) | `required_for` — вычисляемая |
| `part_of` | A→B «A — часть B» | от частного к общему | `has_part` — вычисляемая |
| `related` | симметричная | одна запись | разворачивается при чтении |
| `contrast` | симметричная | одна запись | разворачивается при чтении |

Правило канонического направления для асимметричных связей: обратная сторона — проекция индекса (`derived=1`), не вторая запись.

Правило владения симметричной связью: хранится в ноте, **ранней по `created`; при равных `created` — с лексикографически меньшим `uid`**. Владелец пересчитывается при rebuild; soft-delete владельца не переносит запись и не разворачивает связь — обе стороны по-прежнему видят связь (чтение идёт по edges, а не по владельцу). [Р]

**Хранение (SQLite, без графовой БД):**

```sql
notes(uid PK, kind, title, body, question, answer, sources, schema_version,
      deleted, created, modified, mod, guid, base_hash);
cards(card_uid PK, note_uid, ord, deck, progress_policy, suspended, archived_tag);
edges(src_uid, rel_type, dst_uid, via_note_uid, seq, derived,
      PRIMARY KEY(src_uid, rel_type, dst_uid, seq));
note_provenance(note_uid, run_id, prompt_version, model, published_at);
review_log(ts_ms, card_uid, anki_cid, ease, ivl_days, last_ivl_days, factor, time_s, revlog_type);
tags_aliases(uid, value);
FTS5(title, body);
```

Поле Relations — канонический источник связей; одна связь = одна JSON-строка: `{"t":"requires","to":"n-...","note":"..."}`. **`seq` = порядковый номер строки связи внутри Relations (сверху вниз), назначается при rebuild и не хранится в самом JSON.** `edges` — перестраиваемый индекс, включая вычисленные инверсии (`derived=1`). Детект циклов (Tarjan) на rebuild: `part_of`-цикл — ошибка данных (флаг + отчёт, импорт не блокируется); `requires`-SCC отдаётся планировщику как пакет. Висячие связи не удаляются — плейсхолдер missing; при появлении ноты связь «оживает».

Пересмотр графовой БД — при появлении интерактивных layout-запросов по всему графу. Оценка «CTE достаточно для ≤10k узлов» — порядок величин, не бенчмарк; проверяется Э5. [Г]

## 6. Пример набора

Материал: статья «Фермент: кинетика Михаэлиса–Ментен» (`m-ferment-kinetics-a1b2`).

**Заметка 1 (concept):**
```yaml
uid: n-018f3a2b-7c41-7000-8000-000000000001
schema_version: 1
kind: concept
title: Кинетика Михаэлиса–Ментен
body: "Модель скорости ферментативной реакции: v = Vmax·[S]/(Km+[S]) …"
question: Что означает Km в уравнении Михаэлиса–Ментен?
answer: Концентрация субстрата, при которой скорость равна половине Vmax.
sources:
  - {ref: m-ferment-kinetics-a1b2, locator: "стр. 12"}
relations:
  - {t: requires, to: n-018f3a2b-7c41-7000-8000-000000000002}
  - {t: part_of,  to: n-018f3a2b-7c41-7000-8000-000000000003}
```

**Заметка 2 (concept; все обязательные поля по §7 заполнены — в ред. 1 отсутствовали schema_version и body):**
```yaml
uid: n-018f3a2b-7c41-7000-8000-000000000004
schema_version: 1
kind: concept
title: Ингибиторы конкурентные vs неконкурентные
body: "Конкурентный ингибитор связывается с активным центром …"
question: Как влияет конкурентный ингибитор на Km и Vmax?
answer: Km растёт, Vmax не меняется.
sources:
  - {ref: m-ferment-kinetics-a1b2, locator: "стр. 14"}
relations:
  - {t: requires, to: n-018f3a2b-7c41-7000-8000-000000000001}
  - {t: contrast, to: n-018f3a2b-7c41-7000-8000-000000000005}
```

Граф: `Ингибиторы --requires--> Кинетика --requires--> Фермент`, `Кинетика --part_of--> Биохимия`, `Конкурентные --contrast--> Алостерические`. Карточки: **в MVP по умолчанию ровно 1 карточка на заметку** (правило ord-сопоставления §8.2 упрощается); несколько карточек на заметку допустимы, но включаются осознанно (§8.2).

## 7. Обменный формат и отображение в поля Anki

Обменный формат: Markdown + frontmatter, один файл = одна заметка (пример — §6; обязательные поля: uid, schema_version, kind, title, body, question, answer, sources, relations; question/answer/sources/relations допускают пустые значения, но ключи обязательны).

Отображение в нотетайп ObsidianTyped:

| Поле Anki | Источник | Примечание |
|---|---|---|
| 1. UID | `uid` | ключ дедупликации текстового импорта [Ф] |
| 2. Title | `title` | display-only |
| 3. Body | body, markdown→HTML | |
| 4. Question / 5. Answer | `question`/`answer` | |
| 6. Relations | JSON-строки | в Answer рендерится плоско: «Связано: …» |
| 7. Sources | JSON | |
| 8. SchemaVersion | `schema_version` | конвертеры отказываются работать с неизвестной версией |

GUID пакета = детерминированная кодировка `note_uid`. Тег `archived:<run_id>` кладётся в **note.tags** (метаданные заметки, не поле нотетайпа — §2). Media — контентно-адресованные имена (SHA-256), ASCII.

### 7.1. HTML-подмножество (фиксируется контрактом)

MVP использует и генерирует только: абзацы, **жирный/курсив**, списки (ul/ol), ссылки (внешние http(s)), инлайн-код и блок кода, изображения `<img>` по именам media. **Исключено из MVP: таблицы, математика (MathJax/LaTeX), JS, кастомные фильтры.** Любое расширение подмножества — через SchemaVersion и прогон Э2 в трёх клиентах. Рендер этого подмножества в живых клиентах не проверялся — Э2. [Г]

## 8. Контракт обновления и разрешение конфликтов

**Идентификация.** Всё по UID (+guid). Отсутствие в выходе агента ≠ удаление; удаление — только явная `deletions` с reason. **`op: touch` обновляет только `note_provenance` и `modified`, не трогая контент и mod.**

**Потоки (фиксированы, однонаправлены):**

1. **Контент:** БД сервера. Две точки правки: публикация агента и **ручное редактирование в приложении (§9, сценарий 9)**. После любой из них — регенерация .apkg и markdown-архива.
2. **Scheduling — мерж по соответствию КАРТА↔КАРТА, не по UID заметки** (поправка к ред. 1: revlog Anki привязан к cid, мерж «по UID» при n>1 карточках на заметку неоднозначен):
   - По умолчанию MVP: **1 карточка на заметку** → соответствие тривиально: Anki-карта ноты ⇔ наша карта с ord=0.
   - При n>1: соответствие по паре **(note.guid, ord)**; число/порядок карточек нотетайпа менять после первого экспорта нельзя — если изменение числа карточек необходимо, применяется `suspend_and_new` для всех карт ноты и пере-маппинг с ручным подтверждением в приложении.
   - Прогресс мержится полем: due (дни), interval, ease/factor; для suspended-карт состояние переносится как suspended.
3. **Конфликт контента И СВЯЗЕЙ:** `base_hash` = sha256(title+body+relations+sources). При расхождении текущего base_hash с известным агенту — правка (контентная или в Relations) уходит в `conflicts/`, автоматического мержа нет. Режимы `edit_protection`: `protected` / `agent_merge` / `open` (для open — трёхсторонний merge по полям, неразрешимое — в review).
4. **Markdown-экспорт** — read-only; правки в нём — через конфликт-пайплайн.
5. **SchemaVersion** инкрементится при несовместимых изменениях; миграции — явные скрипты.
6. **Прогресс карточек:** близость ≥ 0.92 → `preserve` (та же карта, тот же guid, scheduling сохранён [Ф: text-files.html] — сам порог эвристика [Г]); смена смысла → `reset` или `suspend_and_new`: старая карта помечается `suspended=1` в нашей БД и получает **note.tags** `archived:<run_id>` в .apkg; удаление карты агентом без explicit task запрещено — только suspend.
7. **Различение нового/существующего агентом:** экспорт-индекс сервера; совпадение Title/alias → существующий UID; неуверенность → `merge_candidate` + related-связь → очередь мержей.
8. **Несовместимость планировщиков (добавлено):** приложение считает по swift-fsrs (FSRS-6), Anki может работать на SM-2 или FSRS с другими весами. Правило консервативного мержа: из Anki переносим только **due/interval/suspended** как сырые значения; семантические состояния FSRS (stability/difficulty) из Anki не переносим; при источнике SM-2 помечаем карту флагом `legacy_scheduler` и пересчитываем стабильность из истории revlog лениво (или оставляем due-управление как есть). Соответствие состояний learning/ease ↔ FSRS первично не проверено — **эксперимент Э6**. [Г]

## 9. Сценарии и экраны iOS

**Сценарии:**
1. Синхронизация: запуск / pull-to-refresh / silent push → pull дельт по `since=version`.
2. Обучение: очередь SRS (swift-fsrs) → карточка в WKWebView → Again/Hard/Good/Easy → review_log; батчевый push.
3. Навигация: заметка → связи (входящие/исходящие), backlinks, переход по связи (навигация, не повторение).
4. Граф: текущая заметка + соседи 1-го порядка (SwiftUI Canvas), zoom-out до кластеров.
5. Зависимое обучение (софт): бейдж «возможно, рановато»/приоритет внутри дня; preview без записи revlog; SCC — пакетом. Ничто не блокируется.
6. Cram: отдельная таблица `training_reviews`, не влияет на due.
7. Очередь мержей (`merge_candidate`): объединить / оставить оба / перенаправить связи.
8. Конфликты: просмотр `conflicts/` (контент и Relations) → принять версию.
9. **Ручное редактирование (добавлено): экран «Редактор заметки»** — правка Body/Question/Answer/Title и связей в приложении. Правка инкрементирует `manual_revision`, пересчитывает `base_hash` и по умолчанию переводит `edit_protection` в `protected`; правки Relations проходят через тот же конфликт-пайплайн при следующей публикации агента. Именно этот сценарий — источник «ручных правок», с которыми сталкивается §8.3.

**Экраны:** Home/Обучение · Карточка (WKWebView + scheme handler) · Заметка · **Редактор заметки** · Граф (Canvas) · Поиск (FTS5) · Библиотека (PDFKit) · Синхронизация/Настройки · Мержи · Конфликты.

Стек: Swift 6 + SwiftUI; GRDB.swift 7.x; swift-fsrs (FSRS-6); оптимизация весов (fsrs-rs) — на сервере; WKWebView + Mustache/Stencil; минимум iOS 17.

**Фоновая синхронизация — пессимистично:** гарантии — on-demand и silent push через APNs; BGAppRefresh запрашиваем, не полагаемся. Точные лимиты BGTaskScheduler не проверялись в этой сессии — взять из документации Apple при имплементации. [Г]

**Сервер (стек выбран, добавлено):** Python 3.12 + FastAPI — совпадает с genanki (генерация .apkg) и пайплайном агента; один монолит-процесс, SQLite WAL, reverse-proxy Caddy; restic на объектное хранилище. [Р]

**Бэкапы (схема, добавлено):** (1) `sqlite3 .backup` после каждой публикации + хранить N последних; (2) медиа content-addressed — restic-инкремент раз в сутки на объектное хранилище; (3) monthly test restore: разворачивание бэкапа в docker на ноутбуке + импорт полученного .apkg в чистый AnkiDesktop. [Р]

## 10. Границы MVP и последующих версий

**В MVP:** сервер (публикация агента, delta-sync, .apkg-генерация, anki sync-server рядом, APNs-push, бэкапы по схеме §9); обменный формат v1 + два однонаправленных конвертера; iOS: импорт, карточки, FSRS-обучение, навигация, backlinks, локальный граф, поиск, Cram, редактор заметки, мержи, конфликты; 4 типа связей; нотетайп ObsidianTyped — **состав фиксируется после Э1**.

## 12. Риски и технические эксперименты

**Риски:**

| Риск | Митиг |

| Рендер HTML-подмножества расходится между клиентами | Минимальное подмножество §7.1; Э2 |
| Несанкционированная правка Relations при ручном редактировании | base_hash включает Relations (§8.3); редактор инкрементирует manual_revision |
| «AnkiMobile не поддерживает дополнения» — [Ф2] | На архитектуру не влияет (уровень 3 не строится на дополнениях) |
| LE IP-сертификаты: статус на 2026-11-01 не верифицирован | Базовый план self-signed+pinning; Tailscale — альтернатива |
| Порог близости 0.92 не откалиброван [Г] | Зона 0.85–0.92 → review; калибровка на реальном материале |
| CTE/Canvas-производительность не измерялась [Г] | Э5 |

**Эксперименты:**

**Э1 — полный цикл (ключевой).** Окружение: ноутбук + AnkiDesktop + genanki.

1. *Создание.* Скрипт генерирует `test1.apkg`: нотетайп ObsidianTyped (8 полей, UID первым), 2 заметки из §6 (UID `…0001`, `…0004`, связь requires), guid = base91(sha256(uid)[:8]), mod = T0, по 1 карточке на заметку. *Ожидаемо:* импорт в пустую коллекцию — 2 заметки, 2 карточки; Relations виден как текст; Q/A отвечаются.
2. *Обучение.* Повторить обе карточки: Good обеим; одна — в learning. *Ожидаемо:* due/interval изменились, revlog содержит 2 записи.
3. *Экспорт.* `test2.apkg`, Include Scheduling = True. *Ожидаемо:* пакет содержит те же guid/UID и revlog.
4. *Обновление.* Изменить Body и Relations заметки `…0001` (тот же uid/guid, **mod = T1 > T0**), собрать `test3.apkg`, импортировать с «Import any learning progress». *Ожидаемо:* «2 notes updated, 0 added»; контент и связи обновились; **планирование сохранилось**.
5. *Отрицательный контроль — дубли.* Повторный импорт `test3.apkg`. *Ожидаемо:* 0 added, 0 updated; дублей нет.
6. *Отрицательный контроль — смена типа.* Пакет с добавленным полем (другой notetype id). *Ожидаемо:* заметка игнорируется/конфликт типов — подтверждение риска «поля заморожены».
7. *Восстановление связей.* Обратный конвертер: `test2.apkg` → exchange → чистая БД приложения. *Ожидаемо:* edges содержит 1 каноническую связь `…0004 requires …0001` + инверсию derived=1.
8. *Мерж прогресса.* Из `test2.apkg` извлечь revlog и смержить **по правилу (guid, ord)**: карта ноты `…0001` (ord 0) → наша карта ord 0. *Ожидаемо:* due/interval нашей карты равны AnkiDesktop-значениям; контент — новый.
9. *Критерий успеха:* ни одного дубля, ни одной потерянной записи прогресса, связи восстановлены по UID, тип нотетайпа не изменился.

**Э2 — рендер-совместимость §7.1.** Тот же .apkg в AnkiDroid/AnkiMobile/AnkiDesktop: Q/A, HTML-подмножество, Relations как текст, media. *Ожидаемо:* одинаково читаемо; расхождения → сузить подмножество.

**Э3 — sync-server + AnkiMobile.** Поднять `anki --syncserver`, подключить AnkiDroid (`http://<ip>:8080`), повторить, синк, реимпорт обновления. *Ожидаемо:* прогресс переживает синк и реимпорт. Отдельно: проверить наличие и работу custom sync URL в AnkiMobile на устройстве/в App Store описании — **результат Э3 — вход для решения об уровне 2 для AnkiMobile**.

**Э4 — TLS.** Self-signed ECDSA P-256 + SPKI-pinning (SHA-256 публичного ключа, `didReceiveChallenge`); ротация сертификата с тем же ключом. *Ожидаемо:* соединение проходит; ротация не требует апдейта приложения.

**Э5 — масштаб.** 5–10k заметок × ~2 связи: rebuild edges, CTE-соседи, Canvas ~300 узлов на iPhone. *Ожидаемо:* rebuild < секунды; навигация без ощутимых лагов.

**Э6 — мерж планировщиков (добавлено).** Коллекция AnkiDesktop в режиме FSRS и в режиме SM-2: экспорт, извлечение revlog/due, прогон через swift-fsrs `next()`. *Ожидаемо:* определить корректный маппинг состояний; зафиксировать колонки revlog и семантику типов записей по фактической схеме collection.anki2. Если маппинг неоднозначен — уровень 2 прогресс для Anki держим «due-управлением» без переноса FSRS-состояний.
