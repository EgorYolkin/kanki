# Э1: проверка обмена с AnkiDesktop

Это **эксперимент**, а не формат обмена приложения. Его восьмиполевый нотетайп и ID нельзя считать утверждёнными до полного прогона на AnkiDesktop. Используйте отдельный временный профиль Anki, без личной коллекции.

## Подготовка

Нужны AnkiDesktop и `uv`. Пакеты генерируются вне репозитория (не коммитьте `.apkg` с личными данными):

```bash
uv run --no-project --with genanki==0.13.1 python experiments/e1.py generate /tmp/kanki-e1
uv run --no-project --with genanki==0.13.1 python experiments/e1.py inspect /tmp/kanki-e1/test1.apkg
```

`test1.apkg` содержит две заметки/карточки, UID первым полем, одну связь `…0004 requires …0001`. `test3.apkg` сохраняет guid и ID нотетайпа, но увеличивает `mod`, меняет Body и Relations заметки `…0001`; обе заметки в пакете получают новый `mod`. `test4-type-change.apkg` — отрицательный контроль: тот же guid заметки `…0001`, другой нотетайп с дополнительным полем. `genanki.guid_for(uid)` использует base91 от первых 8 байтов SHA-256; это проверяемая гипотеза контракта, не продуктовая гарантия.

## Ручной прогон (отметить фактические результаты в issue #3)

1. Импортировать `test1.apkg` в **пустой временный профиль** AnkiDesktop: проверить 2 заметки, 2 карточки, читаемые Q/A и Relations.
2. Ответить Good на обе карточки; проверить изменившиеся due/interval и записи истории повторов. Учесть различие состояния learning/review.
3. Экспортировать колоду как `/tmp/kanki-e1/test2.apkg` **с историей повторений**. Проверить содержимое: `uv run --no-project --with genanki==0.13.1 python experiments/e1.py inspect /tmp/kanki-e1/test2.apkg`. Сопоставить по guid и ord; сверить фактическое число revlog и due/interval. Это выход AnkiDesktop, а не genanki.
4. Импортировать `test3.apkg` с включённым сохранением прогресса обучения (наименование переключателя зависит от версии Anki). Проверить число обновлённых/добавленных заметок, Body/Relations, due/interval и revlog **до и после**. Не считать сохранение прогресса доказанным только по сообщению импорта.
5. Импортировать `test3.apkg` ещё раз: проверить отсутствие дублей и повторных изменений. Импортировать `test4-type-change.apkg`: зафиксировать фактическую реакцию на несовпадающий нотетайп, число добавленных/обновлённых заметок и состояние исходной.
6. Извлечь Relations из `test2.apkg` через `inspect` и проверить каноническое ребро `…0004 requires …0001`; вычисленная обратная проекция `required_for` должна строиться индексом приложения, её нет в .apkg. Сопоставить карты по `(guid, ord)`.

**Успех Э1:** нет дублей, прогресс не потерян, UID/GUID и связи восстановимы, конфликт типа обработан предсказуемо. Если любое ожидание расходится с фактом — записать расхождение, а не менять продуктовый контракт молча. Здесь нет реальной БД Kanki, обратного конвертера и автоматического мержа: соответствующие пункты Э1 остаются открытыми до их реализации и проверки.
